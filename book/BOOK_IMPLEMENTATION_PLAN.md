**项目名称**: AI Context Engineer 视角下的现代编译器实战：用 Java/ANTLR4 + AI 共同实现一门语言
**规划日期**: 2026-01-12
**版本**: 1.0
**状态**: 草案

## 一、项目背景与定位

### 1.1 项目概述

基于开源项目 `How_to_implment_PL_in_Antlr4`，撰写一本面向 1–5 年经验工程师的技术书，从 ANTLR4 基础开始，逐步构建完整的现代编译器，重点展示 AI 协作工作流。
项目代码根目录在当前文件夹的父目录中。
### 1.2 核心特色

**双线叙事**:
- **人类工程师线**: 正常的编译器构造实践（概念 + 代码 + 实验）
- **AI 协作线**: 如何设计上下文（Context），让 AI 安全、高效地参与每一章任务

**技术深度**: 从基础解析器到研究级优化（SSA、数据流分析、尾递归优化）

**实战导向**: 每章都有可运行的代码示例和测试，完整的编译器流水线实现

## 三、仓库上下文分析

### 3.1 EP（Episode）结构概览

**Phase 1: 基础语言与解释器 (EP1–EP12)**
- 目标: 学习 ANTLR4 基础，构建解释器
- 关键概念: 词法分析、语法解析、访问者模式、AST 基础、符号表初步
- 输出: 可执行的 Cymbol 解释器

**Phase 2: 编译基础 (EP13–EP16)**
- 目标: 从解释转向编译，实现语义分析
- 关键概念: 多遍编译、符号表系统、类型检查
- 输出: 静态类型检查的编译器前端

**Phase 3: 现代编译器架构 (EP17–EP21)**
- 目标: 构建生产级编译器，实现高级优化
- 关键概念: 调用图、虚拟机、IR、CFG、SSA、数据流分析、尾递归优化
- 输出: 完整优化的编译器流水线

### 3.2 技术栈

| 组件 | 技术 | 版本 |
|--------|-------|------|
| 语言 | Java | 21 |
| 解析器生成器 | ANTLR4 | 4.13.2 |
| 构建工具 | Maven | 3.8+ |
| 测试框架 | JUnit Jupiter | 5.8.2 |
| 断言库 | AssertJ | 3.21.0 |
| 日志 | Log4j2 | 2.17.1 |
| 图算法库 | JGraphT | Latest |

### 3.3 编译器流水线架构

```
源代码 (Cymbol)
    ↓
词法分析 (Lexer)
    ↓
语法分析 (Parser)
    ↓
AST 构建 (AST Builder)
    ↓
符号解析 (Symbol Resolution)
    ↓
类型检查 (Type Checker)
    ↓
IR 生成 (IR Generation - MIR/LIR)
    ↓
CFG 构建 (CFG Construction)
    ↓
数据流分析 (Dataflow Analysis)
    ↓
SSA 转换 (SSA Conversion) ← EP21 特有
    ↓
优化 Pass (Optimization Passes)
    ↓
代码生成 (Code Generation)
    ↓
VM 字节码 (VM Bytecode)
    ↓
虚拟机执行 (VM Execution)
```

## 五、AI 协作线设计

### 5.1 每章标准 AI 协作内容

#### 5.1.1 上下文设计

每章必须包含：
1. **源码上下文**: 需要提供给 AI 的具体文件列表
2. **测试上下文**: 相关测试用例和预期行为
3. **文档上下文**: 相关设计文档、README、规范

**示例**:
```
对于第 14 章（CFG 构建），需要提供以下上下文：
- 源码: ep20/src/main/java/org/teachfx/antlr4/ep20/pass/cfg/CFGBuilder.java
- 测试: ep20/src/test/java/org/teachfx/antlr4/ep20/pass/cfg/BasicBlockTest.java
- 文档: ep20/docs/01_core_design/EP20_项目架构设计规范.md
- 示例输入: ep20/src/main/resources/simple_test.cymbol
```

#### 5.1.2 Prompt 模板

每章提供 1–2 个可直接复用的 Prompt 模板：

**类型 A: 功能实现 Prompt**
```
请在不破坏现有语法的前提下，为 Cymbol 语言增加 [新语法特性]。

要求：
1. 修改 Cymbol.g4 语法文件，添加 [生产规则]
2. 更新相关的 AST 节点类
3. 实现对应的 Visitor 方法
4. 添加测试用例验证功能

参考上下文文件：
- [文件列表]
```

**类型 B: 优化实现 Prompt**
```
请根据以下优化规则，将这段三地址码转换为优化形式：

[输入代码]

优化目标：
1. 常量折叠：计算编译时常量表达式
2. 死代码消除：移除未使用的赋值
3. 公共子表达式消除：识别并合并重复计算

请返回：
1. 优化后的代码
2. 变化的解释说明
```

**类型 C: 测试生成 Prompt**
```
请为 [功能模块] 生成一组完整的测试用例，覆盖以下场景：
1. 正常情况
2. 边界情况
3. 错误情况

要求：
- 使用 JUnit 5 和 AssertJ
- 提供 @DisplayName 注解的中英文描述
- 包含参数化测试用例
```

#### 5.1.3 验证与回滚策略

每章必须说明：
1. **自动化验证**:
   - 运行哪些测试命令（`mvn test -Dtest=XXXTest`）
   - 检查哪些关键指标（测试通过率、覆盖率）

2. **手工检查点**:
   - 代码风格是否符合规范（见 AGENTS.md）
   - 是否引入新的编译错误
   - 是否破坏现有功能

3. **回滚方案**:
   ```bash
   # 如果 AI 修改后出现问题，快速回滚
   git stash save "AI changes"
   git stash pop  # 恢复到修改前状态
   ```

### 5.2 AI 应该做 / 不该做

**允许 AI 做的事情**:
- ✅ 实现明确界定的功能模块
- ✅ 生成测试用例和辅助代码
- ✅ 优化特定算法实现（如 SSA 转换）
- ✅ 生成代码注释和文档
- ✅ 重命名变量和方法，提升可读性

**禁止 AI 做的事情**:
- ❌ 大规模重构目录结构
- ❌ 修改核心接口定义（除非明确要求）
- ❌ 删除测试用例或降低测试覆盖率
- ❌ 修改编译器流水线架构
- ❌ 破坏现有 EP 模块边界

## 七、技术难点与解决方案

### 7.1 编译器复杂度管理

**挑战**: 从基础解析器到研究级优化的跨度巨大

**解决方案**:
1. **渐进式学习路径**: EP 划分明确，每章聚焦 1-2 个核心概念
2. **多角度解释**: 概念讲解 → 代码实现 → 图表可视化 → 实战示例
3. **"你现在站在哪"总结**: 每章结尾明确当前在编译器流水线的位置

### 7.2 AI 协作的平衡

**挑战**: 如何让 AI 辅助而不掩盖学习价值

**解决方案**:
1. **明确 AI 边界**: 每章清晰列出允许/禁止事项
2. **分层 Prompt 设计**: 从简单到复杂，逐步让读者理解如何与 AI 交互
3. **验证优先**: 强调测试驱动开发，AI 修改必须经过验证
4. **回滚机制**: 提供简单的 git 回滚策略，降低试错成本

### 7.3 内容连贯性

**挑战**: 21 个 EP 横跨多个技术主题

**解决方案**:
1. **模块化组织**: 5 个模块，每模块内部强关联
2. **跨章引用**: "第 X 章详细讲解了...，这里直接使用"
3. **渐进式示例**: 同一个程序（如斐波那契数列）在不同章节展示不同编译阶段
4. **流水线图示**: 每章标注当前在流水线中的位置
